# PIE 本地存档

绿洲启元编辑器在 PIE（Play In Editor）模式下提供一套完整的存档系统：DS（Dedicated Server）侧的玩家存档数据可与本地 `.json` 文件双向同步，编辑器侧提供基于 UID 的存档选择器 UI，让每个 PIE 客户端在启动时独立指定使用哪份存档。本文档面向玩法开发者的日常 PIE 调试场景，覆盖 UID 计算规则、启动 PIE 时选档、运行中新增客户端、存档文件格式与排障日志关键词等关键链路。<br>


<br>

## 一、功能概述

UGC PIE 存档系统支持在 PIE 模式下，将 DS（Dedicated Server）上的玩家存档数据与本地文件互相同步，并提供基于 UID 的选择器 UI，让用户为每个 PIE 客户端独立指定使用哪份存档。

核心能力：

- **上传存档**：将本地 `.json` 存档文件上传到 DS，DS 接收后分块存储。
- **下载存档**：DS 主动推送存档数据到编辑器，编辑器写入本地 `.json` 文件，实现 PIE 跨局存档继承的能力。
- **多玩家支持**：每个 PIE 客户端持有独立 UID，可独立选择不同存档，互不干扰。


<br>

## 二、UID 计算规则

UID 是存档系统的核心标识，用于区分不同玩家的存档数据。
>本节主要面向排查 UID 冲突、理解存档文件名含义的场景；仅关心"如何选档 + 跑 PIE"的开发者可跳过本节。



### 2.1 普通玩家

```text
UID = TeamId × UIDMultiplier + ClientId
UIDMultiplier = 10000
```
其中 `UIDMultiplier = 10000`，为固定常量，目的是保证不同队伍的 UID 区段不重叠。

| 参数 | 类型 | 说明 |
|------|------|------|
| `TeamId` | `int32` | 队伍编号，从 `1` 开始 |
| `ClientId` | `int32` | 队伍内的客户端编号，从 `1` 开始 |
| `UIDMultiplier` | `int32` | 固定常量 `10000` |

示例：

| TeamId | ClientId | UID |
|--------|----------|-----|
| 1 | 1 | 10001 |
| 1 | 2 | 10002 |
| 1 | 3 | 10003 |
| 2 | 1 | 20001 |
| 3 | 1 | 30001 |

<br>

### 2.2 队伍内 OB（观察者）

OB 玩家的 UID 紧跟本队普通玩家 UID 之后分配，避免与普通玩家冲突：
```text
OB_UID = TeamId × UIDMultiplier + PlayerCount + OBIndex + 1
```
| 参数 | 类型 | 说明 |
|------|------|------|
| `TeamId` | `int32` | 队伍编号 |
| `PlayerCount` | `int32` | 该队伍中普通玩家总数 |
| `OBIndex` | `int32` | OB 在该队伍中的序号，从 `0` 开始 |
| `+1` | — | 偏移量保证 OB UID 紧跟最后一个普通玩家 UID |

示例：某队伍 `PlayerCount = 4`，OB 共 2 个（`OBIndex` 分别为 `0`、`1`）：

| TeamId | PlayerCount | OBIndex | OB_UID |
|--------|-------------|---------|--------|
| 1 | 4 | 0 | 10005 |
| 1 | 4 | 1 | 10006 |
| 2 | 4 | 0 | 20005 |

> `PlayerCount` 配置必须准确，否则 OB UID 会与下一 UID 区段的玩家产生冲突。

<br>

### 2.3 房间 OB

`RoomOB_UID = 10000`（固定值）

房间 OB 全局唯一，始终占用 `TeamId=1` 区段内、`ClientId=0` 之后的位置（`10000`），表示房间级别的观察者，与队伍内 OB 区分开。

<br>

## 三、启动 PIE 时使用存档

### 3.1 操作步骤

在编辑器中启动 PIE 调试时，通过 **PIE Client Manager Toolbar** 完成玩家配置与存档选择。

1. 在绿洲启元编辑器主界面打开 **PIE Client Manager Toolbar**（PIE 客户端管理工具栏）。
2. 在工具栏中配置本次 PIE 的玩家信息：`TeamCount`（队伍数）、`PlayerCount`（每队玩家数）、`OB` 数量等。
3. 为每个玩家（每个 UID 槽位）选择存档文件：
   - **ComboBox 下拉列表**：自动扫描本地 `ArchiveData` 目录下的 `.json` 文件，并以文件名（UID）形式列出可选存档。
   - **留空槽位**：表示不指定本地存档，系统在 DS Ready 后等待 DS 推送该 UID 的存档数据。
4. 点击 **Start** 启动 PIE，DS 启动后即按选择规则处理存档。


<img src="https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/5oDaZimage.png" width="700" />


<br>

### 3.2 存档选择规则

| 槽位状态 | 处理动作 |
|----------|----------|
| 选择了一个本地 `.json` 文件 | 读取本地 `.json`，解析后上传到 DS，DS 分块存储。存档将以该本地文件内容为初始值。 |
| 留空（未选择） | 该 UID 加入「待拉取列表」；DS Ready 后，DS 主动推送存档数据到编辑器，编辑器写入本地 `.json` 文件（覆盖或新建，取决于本机是否已有同名文件）。 |



<br>

## 四、运行中加入新客户端

PIE 运行中如有新客户端加入，系统通过 **PIE Manager** 窗口单独处理新客户端的存档，**不影响已运行的存量客户端**。<br>

### 4.1 操作步骤

1. **新客户端 UID 自动计算**：根据 `TeamId`、`ClientId` 按普通玩家（§2.1）或 OB（§2.2）规则计算。
2. **追加到存档选择列表**：新 UID 槽位默认追加在列表末尾，默认状态为空（`（无）`），由开发者在工具栏中按需选择。
3. **针对单 UID 上传**：单独处理新增 UID 的上传，不影响已运行的其他客户端存档。
4. **存档服务未就绪处理**：若 DS 此刻未 Ready，该 UID 进入「待上传队列」，DS Ready 后由系统统一触发上传。


<img src="https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/eD2PIimage.png" width="800" />
<br>

### 4.2 与「Start」场景的区别

| 场景 | 处理范围 | 对存量客户端影响 |
|------|----------|------------------|
| Start | 一次性处理所有 UID（含房间 OB） | — |
| 运行中 Join | 只处理新增的单一 UID | 完全不影响；存量客户端存档不会被重传或覆盖 |

## 五、存档文件

### 5.1 保存实机

存档文件将在开始存档请求[SavePlayerArchiveData](https://developer.gp.qq.com/api/#/searchContent/UGCPlayerStateSystem?classDetailShow=true&path=class%2Fdetail%2F%E5%92%8C%E5%B9%B3%E5%85%A8%E5%B1%80%E6%8E%A5%E5%8F%A3%2F%E8%A7%92%E8%89%B2%E7%B3%BB%E7%BB%9F%2FUGCPlayerStateSystem.json&isSelect=1&apiEnc=%5B%22%E7%B1%BB%22%5D&apiLabel=UGCPlayerStateSystem&autoJump=SavePlayerArchiveData)时，自动进行更新保存
<br>

### 5.2 保存目录

存档文件保存在项目 Saved 目录下的 `ArchiveData/{ProjectName}/` 目录：
```text
{ProjectSavedDir}/ArchiveData/{ProjectName}/{uid}.json
```
示例（含 OB 文件）：

```text
O:\O\Trunk\Saved\ArchiveData\MyProject\
    ├── 10000.json   # 房间 OB
    ├── 10001.json   # TeamId=1, ClientId=1 的存档
    ├── 10002.json   # TeamId=1, ClientId=2 的存档
    ├── 20001.json   # TeamId=2, ClientId=1 的存档
    └── 10005.json   # TeamId=1 的第一个 OB 存档
```

| 路径段 | 说明 |
|--------|------|
| `{ProjectSavedDir}` | 项目 Saved 目录，通常形如 `......\Saved\` |
| `ArchiveData` | 存档数据根目录，**固定名称** |
| `{ProjectName}` | 项目名称，用于隔离不同项目 |
| `{uid}` | 玩家 UID，作为文件名（按 §二 计算） |


<br>

### 5.3 文件格式

存档文件采用 JSON 格式，呈「三层嵌套」结构 `uid → seq → chunk object`，第三层为任意键值对：

```json
{
  "10001": {
    "1": {
      "write_count": 5,
      "timestamp": 1785407758
    }
  }
}
```

| 层级 | 键类型 | 说明 |
|------|--------|------|
| 第一层 | `uid` (`string`) | 玩家 UID。**JSON 中使用字符串键**，即便 UID 是数字 |
| 第二层 | `seq` (`string`) | 分块序号，从 `1` 开始递增 |
| 第三层 | 任意键 | 分块数据。键和值的含义由游戏逻辑定义，无固定字段模式 |



<br>

## 六、常见使用场景


### 场景一：单人功能测试

- **配置**：1 队 1 人；UID = `10001`
- **存档选择**：可选一份现成本地 `.json`（覆盖），或留空从 DS 拉取
- **适用**：单人功能验证、存档读写调试、断点排查

### 场景二：多人对战测试

- **配置**：2 队各 4 人；UID `10001~10004`、`20001~20004`
- **存档选择**：每个 UID 可独立选档，便于复现「队伍 A 有背包、队伍 B 无背包」这种非对称初始状态
- **适用**：多人对战逻辑测试、存档隔离验证

### 场景三：带观察者测试

- **配置**：1 队 4 玩家 + 2 OB + 1 房间 OB
  - 普通玩家 UID：`10001~10004`
  - 队伍内 OB UID：`10005`、`10006`
  - 房间 OB UID：`10000`
- **适用**：观战系统测试、OB 端存档独立性验证、OB 行为与玩家行为差异验证



<br>

## 七、注意事项


- **编码一致性**：本地存档必须为 **UTF-8** 编码的 JSON 文件，否则解析失败，会导致 DS 端拒绝存储或读取异常。
- **UID 唯一性**：`UIDMultiplier=10000` 保证普通玩家 UID 区段不重叠；OB UID 紧跟本队普通玩家，**`PlayerCount` 配置必须准确**（少配会导致 OB UID 与下一 UID 区段的玩家产生冲突）。
- **存档文件清理**：系统**不会自动删除** `ArchiveData` 目录下的旧存档，需开发者手动清理；残留旧文件可能导致下次 PIE 自动加载到非预期的存档。
- **PIE 运行中 Join 的存量保护**：§四的 Join 流程只处理新 UID，**不会**触发存量 UID 的存档重传或覆盖，请勿担心 Join 操作影响已在跑的客户端。

<br>

## 八、诊断与排障

存档系统在日志中提供以下关键关键词，便于 QA / 开发者排查问题。建议在 PIE 启动前打开 [PIE 日志面板](https://developer.gp.qq.com/wikieditor/#/catalog/20353)，用关键词过滤存档相关事件：

| 日志关键词 | 含义 |
|------------|------|
| `[UGCSaveData] LogUidListSummary` | 输出本次 PIE 注册的所有 UID 概览（`UIDCount`、`UIDs` 排序列表、`Changed` 标志） |
| `[UGCSaveData] ValidateChunkDataTable` | 验证上传前存档分块数据完整性（`SeqCount`、`ValidChunks`、`InvalidChunks`） |
| `[UGCSaveData] BuildChunkDataSummary` | 生成存档数据结构化摘要，避免日志过长；超过上限时截断并标注 `...（共 N 个，仅显示前 M 个）` |

> 摘要默认上限：最多展示 6 个 UID 的详细数据、每个 UID 最多 6 个分块、每个分块最多 8 个字段。日志不全时，可在 PIE 日志面板调整过滤或提高日志等级。



排查思路参考：

1. **存档未上传 / ComboBox 选了文件但 DS 端没有读到**：先看 `LogUidListSummary` 是否包含该 UID；再看 `ValidateChunkDataTable` 是否有 `InvalidChunks`；最后检查本地 `.json` 编码是否为 UTF-8。
2. **DS 端有存档但 PIE 客户端没有拉到**：先看 PIE 是否运行到 DS Ready 之后；再看是否有 `[UGCSaveData]` 拉取类日志（如有 `Pull From DS`）；如仍无日志，可参考 [PIE 调试失败原因与解决方案](https://developer.gp.qq.com/wikieditor/#/catalog/20391)。
3. **存档加载到错误的 UID**：核对 `PlayerCount` / `TeamCount` 配置与 §二的 UID 公式，常见错误是 `PlayerCount` 配少了导致 OB UID 撞到下一 UID 区段。

<br>

**涉及API/标识符:** `ChunkIndex`, `GetPlayerArchiveData`, `SavePlayerArchiveData`, `UGCBackPackSystem.AddItem`, `UGCBackPackSystem.GetAllItemData`, `UGCPawnAttrSystem.GetPlayerUID`, `UGCPlayerStateSystem`, `UGCPlayerStateSystem.ClearPlayerArchiveData`, `UGCPlayerStateSystem.GetOfflinePlayerArchiveChunkData`, `UGCPlayerStateSystem.GetPlayerArchiveData`, `UGCPlayerStateSystem.GetPlayerArchiveDataByKey`, `UGCPlayerStateSystem.GetPlayerDataSize`, `UGCPlayerStateSystem.GetTableDataSize`, `UGCPlayerStateSystem.SavePlayerArchiveData`, `UGCPlayerStateSystem.SavePlayerArchiveDataByKey`

# 玩家数据存档

数据存档功能允许开发者将对局中产生的玩家个人数据跨对局、持久化存储，例如玩家获得的装备物品、历史战绩等等，各玩法之间的存档数据相互隔离，因此开发者可以安全地使用存档数据。


## 存档数据结构

存档数据的类型和结构为 [LuaTable](https://www.runoob.com/lua/lua-tables.html)，table中的数据元素支持复合类型，包括数字、字符串等基础数据类型，也可以为数组、字典等复杂嵌套结构数据。

> 建议单玩家的存档数据容量大小不能超过1M。

```lua
SaveData = {}

-- 基础类型元素
SaveData[1] = "Lua"
SaveData["wow"] = "abc"

-- table类型元素
local SubTableData = {}
table.insert(SubTableData,"equip")
table.insert(SubTableData,"avatar")
SaveData["attributeList"] = SubTableData
```

### 分块存储（当前版本暂未开放）

存档系统支持将玩家数据按分块（Chunk）进行组织和存储。每个分块通过 `ChunkIndex`（分块序号）进行标识，开发者可以将不同类型的数据存放在不同的分块中，便于管理和按需读取。

不指定 `ChunkIndex` 时，系统默认使用第 1 块（`ChunkIndex = 1`）进行读写操作。



## 保存存档

### SavePlayerArchiveData

使用 [SavePlayerArchiveData](https://developer.gp.qq.com/api/#/searchContent/UGCPlayerStateSystem?classDetailShow=true&path=class%2Fdetail%2F%E5%92%8C%E5%B9%B3%E5%85%A8%E5%B1%80%E6%8E%A5%E5%8F%A3%2F%E8%A7%92%E8%89%B2%E7%B3%BB%E7%BB%9F%2FUGCPlayerStateSystem.json&isSelect=1&apiEnc=%5B%22%E7%B1%BB%22%5D&apiLabel=UGCPlayerStateSystem&autoJump=SavePlayerArchiveData) 接口存储玩家的存档数据，通过参数 [UID](https://developer.gp.qq.com/wikieditor/#/catalog/352) 标识数据的拥有者。

**生效范围**：服务器

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| UID | number | 是 | 玩家 UID |
| ArchiveData | table | 是 | 要保存的存档数据 |
| ChunkIndex | number | 否 | 分块序号，不传时默认为 1 |

**返回值**：boolean，保存是否成功

```lua
local equipSequence = {}

local playerPawn = self:GetPlayerCharacterSafety()
local allItemData = UGCBackPackSystem.GetAllItemData(playerPawn)
for key, itemData in pairs(allItemData) do
	table.insert(equipSequence, itemData.ItemID)
end

local playerUID = UGCPawnAttrSystem.GetPlayerUID(playerPawn)
UGCPlayerStateSystem.SavePlayerArchiveData(tonumber(playerUID), equipSequence)
```

如果需要将数据保存到指定的分块中，可以传入第三个参数 `ChunkIndex`：

```lua
-- 将装备数据保存到第 1 块
UGCPlayerStateSystem.SavePlayerArchiveData(tonumber(playerUID), equipSequence, 1)

-- 将战绩数据保存到第 2 块
UGCPlayerStateSystem.SavePlayerArchiveData(tonumber(playerUID), battleRecord, 2)
```

### SavePlayerArchiveDataByKey

使用 SavePlayerArchiveDataByKey 接口可以按指定的 Key 保存单个数据项，无需手动获取和拼装完整的存档 table。系统会自动读取当前存档数据，更新对应 Key 的值后整体保存。

**生效范围**：服务器

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| UID | number | 是 | 玩家 UID |
| Key | string | 是 | 要保存的键名 |
| Value | any | 是 | 要保存的值 |
| ChunkIndex | number | 否 | 分块序号，不传时默认为 1 |

**返回值**：boolean，保存是否成功

```lua
local playerUID = UGCPawnAttrSystem.GetPlayerUID(playerPawn)

-- 按 Key 保存玩家的金币数量
UGCPlayerStateSystem.SavePlayerArchiveDataByKey(tonumber(playerUID), "gold", 1000)

-- 按 Key 保存到指定分块
UGCPlayerStateSystem.SavePlayerArchiveDataByKey(tonumber(playerUID), "level", 5, 2)
```

> 需要注意的是，SavePlayerArchiveDataByKey 内部会先读取当前存档再写入，频繁调用时建议直接使用 SavePlayerArchiveData 一次性保存完整数据，以减少不必要的读取开销。


## 获取存档

### GetPlayerArchiveData

调用 [GetPlayerArchiveData](https://developer.gp.qq.com/api/#/searchContent/UGCPlayerStateSystem?classDetailShow=true&path=class%2Fdetail%2F%E5%92%8C%E5%B9%B3%E5%85%A8%E5%B1%80%E6%8E%A5%E5%8F%A3%2F%E8%A7%92%E8%89%B2%E7%B3%BB%E7%BB%9F%2FUGCPlayerStateSystem.json&isSelect=1&apiEnc=%5B%22%E7%B1%BB%22%5D&apiLabel=UGCPlayerStateSystem&autoJump=GetPlayerArchiveData) 接口以获取指定玩家的存档数据。

**生效范围**：服务器

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| UID | number | 是 | 玩家 UID |
| ChunkIndex | number | 否 | 分块序号，不传时默认为 1 |

**返回值**：table，玩家的存档数据

```lua
local playerPawn = self:GetPlayerCharacterSafety()

local playerUID = UGCPawnAttrSystem.GetPlayerUID(playerPawn)
local readArchive = UGCPlayerStateSystem.GetPlayerArchiveData(tonumber(playerUID))
for i = 1, #readArchive do
	UGCBackPackSystem.AddItem(playerPawn, readArchive[i], 1)
end
```

读取指定分块的存档数据：

```lua
-- 读取第 2 块存档数据
local battleRecord = UGCPlayerStateSystem.GetPlayerArchiveData(tonumber(playerUID), 2)
```

### GetPlayerArchiveDataByKey

使用 GetPlayerArchiveDataByKey 接口可以按指定的 Key 获取存档中的单个数据项，无需获取完整存档后手动查找。

**生效范围**：服务器

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| UID | number | 是 | 玩家 UID |
| Key | string | 是 | 要获取的键名 |
| ChunkIndex | number | 否 | 分块序号，不传时默认为 1 |

**返回值**：any，对应 Key 的值；Key 不存在时返回 nil

```lua
local playerUID = UGCPawnAttrSystem.GetPlayerUID(playerPawn)

-- 获取玩家的金币数量
local gold = UGCPlayerStateSystem.GetPlayerArchiveDataByKey(tonumber(playerUID), "gold")

-- 从指定分块获取数据
local level = UGCPlayerStateSystem.GetPlayerArchiveDataByKey(tonumber(playerUID), "level", 2)
```


## 获取离线玩家存档（当前版本暂未开放）

### GetOfflinePlayerArchiveChunkData

使用 GetOfflinePlayerArchiveChunkData 接口可以获取不在当前对局中的玩家的分块存档数据。这是一个异步接口，数据通过回调函数返回。

适用场景包括：查看好友的历史战绩、跨对局的社交互动等需要读取其他玩家存档数据的场景。

**生效范围**：服务器

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| SourceUID | number\|nil | 否 | 请求来源玩家 UID，传 nil 或 0 表示由 DS 自身发起请求；传具体玩家 UID 表示由该玩家发起请求 |
| TargetUID | number | 是 | 目标玩家 UID |
| ChunkSeqList | number[] | 是 | 要读取的分块序号列表 |
| Callback | function | 是 | 回调函数，lua 普通函数或 lambda 函数 |
| CallbackSelf | table | 否 | 回调函数的调用主体，冒号定义的函数（`table:func()`）传入 table；普通函数或 lambda 传入 nil |

**Callback 回调参数说明**：

| 参数 | 类型 | 说明 |
|------|------|------|
| bResult | string | 请求结果，`"ok"` 表示成功，其它值表示失败 |
| SourceUID | number | 请求来源玩家 UID（与入参一致，nil 会转为 0） |
| TargetUID | number | 目标玩家 UID |
| ChunkSeqList | number[] | 请求的分块序号列表（与入参一致） |
| ChunkDataList | table | 分块数据列表，与 ChunkSeqList 一一对应，`ChunkDataList[i]` 为 `ChunkSeqList[i]` 对应的分块数据；请求失败时为 nil |

```lua
-- 示例：读取目标玩家第 1 块存档数据
local sourceUID = UGCPawnAttrSystem.GetPlayerUID(self:GetPlayerCharacterSafety())
local targetUID = 123456789

UGCPlayerStateSystem.GetOfflinePlayerArchiveChunkData(
    tonumber(sourceUID),
    targetUID,
    {1},
    function(bResult, srcUID, tgtUID, chunkSeqList, chunkDataList)
        if bResult == "ok" and chunkDataList then
            local data = chunkDataList[1]
            -- 处理获取到的存档数据
            ugcprint("成功获取离线玩家存档数据")
        else
            ugcprint("获取离线玩家存档数据失败")
        end
    end,
    nil
)
```

> 需要注意的是，此接口为异步接口，数据不会立即返回，需要在回调函数中处理结果。


## 存档数据大小查询

### GetTableDataSize

使用 GetTableDataSize 接口可以计算任意 Lua table 序列化后的字节大小，方便开发者在保存前检查数据是否超过容量限制。

**生效范围**：服务器 & 客户端

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| Data | table | 是 | 要计算大小的 table |

**返回值**：number，序列化后的字节大小；计算失败时返回 -1

```lua
local myData = { gold = 1000, items = {101, 102, 103} }
local dataSize = UGCPlayerStateSystem.GetTableDataSize(myData)
ugcprint(string.format("数据大小: %d 字节", dataSize))
```

### GetPlayerDataSize

使用 GetPlayerDataSize 接口可以获取指定玩家当前存档数据的总字节大小，包含所有分块的数据量。

**生效范围**：服务器

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| UID | number | 是 | 玩家 UID |

**返回值**：number，存档数据的总字节大小；无数据时返回 0

```lua
local playerUID = UGCPawnAttrSystem.GetPlayerUID(playerPawn)
local totalSize = UGCPlayerStateSystem.GetPlayerDataSize(tonumber(playerUID))
ugcprint(string.format("玩家存档总大小: %d 字节 (上限 %d 字节)", totalSize, 256 * 1024))
```

> 建议在保存大量数据前，先使用 GetPlayerDataSize 或 GetTableDataSize 检查数据大小，避免超过 256Kb 的容量上限导致保存失败。


## 清理存档

### ClearPlayerArchiveData

使用 ClearPlayerArchiveData 接口可以清理玩家的存档数据。

**生效范围**：客户端

> ⚠️ 注意：此接口为 GM 指令，仅在测试环境下生效，正式线上环境以及PIE下无法使用。

```lua
UGCPlayerStateSystem.ClearPlayerArchiveData()
```


## 存档调试

存档功能已支持编辑器内 [Debug调试](https://developer.gp.qq.com/wikieditor/?timeStamp=1725589224096#/catalog/307) 与 [移动端测试](https://developer.gp.qq.com/wikieditor/?timeStamp=1729765192241#/catalog/372)，其中Debug调试环境下支持跨DS存储，但仅限一次调试会话内有效。

例如，接入了 [二次匹配](https://developer.gp.qq.com/wikieditor/?timeStamp=1725589224096#/catalog/376) 功能的玩法在一次调试会话内，不同子模式（即不同DS）之间的存档数据可互通，但重启调试后存档数据无法再被读取。

> Debug调试环境下每场对局存储的数据非持久化，每次重新启动调试均会重置数据


## 注意事项

开发者在使用存档功能时需要特别注意以下事项：

- 请勿在 [发送游戏结算数据](https://developer.gp.qq.com/wikieditor/#/catalog/272) 之后调用 SavePlayerArchiveData，否则会出现数据丢档的问题
- 存档数据针对玩家个人，请勿把全局玩家的数据都存储在同一个UID下
- 如果游戏业务中确定需要清除玩家的数据，可以将存档数据置 nil 来实现清空效果，历史态数据无法追溯。在手机的测试环境下，也可以使用 ClearPlayerArchiveData 接口进行调试清理
- 使用分块存储时，请合理规划 ChunkIndex 的分配，避免不同类型数据混用同一分块
- SavePlayerArchiveDataByKey 内部会先读取再写入，高频调用场景建议使用 SavePlayerArchiveData 批量保存
- GetOfflinePlayerArchiveChunkData 为异步接口，请在回调函数中处理数据，不要期望同步获取结果
