# Actor属性复制

绿洲启元基于 UE4 引擎的网络同步体系下，同一个 Actor 在 DS 与多个 Client 上各存在一份；**复制属性**就是 DS 把 Actor 上的数据"推"给 Client 的机制。本文档面向 UGC Lua 开发者，系统介绍四种复制属性类型（`Lifetime` / `RepOnce` / `InitialOnlyList` / `Blacklist`）的声明方式、触发 API 与典型场景，作为 [网络同步系统介绍](https://developer.gp.qq.com/wikieditor/#/catalog/203) 中"属性同步"一节的实操补充。


<br>

---

## 一、什么是复制属性

在多人游戏中，同一个 Actor 在 **DS** 和 **多个 Client** 上各存在一份。**复制属性**就是 DS 把 Actor 上的数据"推"给 Client 的机制。整体流向：

> DS 修改属性 → 触发同步 → Client 收到新值 → Client 逻辑使用新值

UGC 玩法中常见的需要复制的属性：玩家血量/积分/状态、机关开关、任务进度、阶段切换、排行榜数据。

> **基础概念**请参见 [绿洲启元玩法开发框架介绍](https://developer.gp.qq.com/wikieditor/#/catalog/352) 中"DS & Client"一节；本词条聚焦 Lua 侧的声明与触发 API。

<br>

---

## 二、四种复制属性类型

| 类型 | 同步行为 | 典型用途 |
|---|---|---|
| **`Lifetime`** | DS 每次复制时自动比对，有变化就同步 | 高频变化的属性（坐标、状态） |
| **`RepOnce`** | 修改后需主动调用 `DOREPONCE`，下次复制时才比对 | 绝大多数普通属性（**推荐默认使用**） |
| **`InitialOnlyList`** | 首次复制到 Client 时写入初始包，之后不再同步 | 配置类、只在 Actor 出现时需要一次的属性 |
| **`Blacklist`** | 直接禁用差异比对和复制 | 确认不需要同步的属性 |

> **UGC 开发者最常用的是 `RepOnce`**。90% 以上的复制属性变化频率都很低，用 `RepOnce` 能显著降低 DS 开销。

<br>

### 速查：四种类型在 Lua 中的使用形式

核心区别：**声明在哪个函数 + 是否需要主动调用 `DOREPONCE`**。

| 类型 | 声明函数 | 触发方式 | 是否需要 `DOREPONCE` |
|---|---|---|---|
| **`Lifetime`** | `GetReplicatedProperties` | 自动 | ❌ 不需要 |
| **`RepOnce`** | `GetReplicatedProperties`（常配 `Lazy`） | `DOREPONCE` | ✅ 需要 |
| **`InitialOnlyList`** | `GetInitialOnlyListReplicatedProps` | 自动（首次复制时） | ❌ 不需要 |
| **`Blacklist`** | `GetBlackListReplicatedProps` | — | ❌ 永远不复制 |

<br>

#### 1. `Lifetime`（自动同步）

```lua
function MyActor:GetReplicatedProperties()
    return "Health"                       -- 默认 Auto，即 Lifetime
end

function MyActor:TakeDamage(Dmg)
    self.Health = self.Health - Dmg       -- 改值即可，引擎自动比对
end
```


<br>

#### 2. `RepOnce`（按需同步，最常用）

```lua
function MyActor:GetReplicatedProperties()
    return {"CurrentPhase", "Lazy"}       -- 配 Lazy 一起用
end

function MyActor:ChangePhase(NewPhase)
    self.CurrentPhase = NewPhase
    DOREPONCE(self, "CurrentPhase")       -- 不调 Client 收不到
end
```

> 如果属性是 C++/蓝图预声明的（非 Lua 声明），不需要 `GetReplicatedProperties`，直接用 `DOREPONCE_NATIVE(self, "isFoodAdded")`。


<br>

#### 3. `InitialOnlyList`（首次复制专用）

```lua
function MyActor:GetInitialOnlyListReplicatedProps()
    return "LevelID", "Difficulty", "MaxPlayers"
end

function MyActor:ReceiveBeginPlay()
    self.LevelID = 101
    self.Difficulty = 0.8
    self.MaxPlayers = 32                  -- Client 首次看到 Actor 时自动收到，之后不再同步
end
```

<br>

#### 4. `Blacklist`（禁用同步）

```lua
function MyActor:GetBlackListReplicatedProps()
    return "bTearOff", "bCanBeDamaged"    -- 通常是继承自父类、但用不到的属性
end
```

<br>

### Condition 参数

`GetReplicatedProperties` 第三个参数可指定复制条件，常用 `OwnerOnly`（只同步给 Owner Client）：

```lua
function MyActor:GetReplicatedProperties()
    return
        "a",                              -- 默认 Auto
        {"b", "Auto"},                    -- 显式 Auto
        {"c", "Lazy"},                    -- Lazy
        {"d", "Lazy", "OwnerOnly"}        -- Lazy + 只给 Owner 同步
end
```

<br>

### 两个触发 API 对比

| 接口 | 适用属性 | 是否需要 `GetReplicatedProperties` |
|---|---|---|
| `DOREPONCE(self, name)` | Lua 声明的属性 | 是 |
| `DOREPONCE_NATIVE(self, name)` | C++/蓝图预声明的属性 | 否 |

> **口诀**：Lua 自己的属性用 `DOREPONCE`，引擎给的属性用 `DOREPONCE_NATIVE`。

<br>

### 一句话总结

> **自动同步** → `GetReplicatedProperties` + 不调用 `DOREPONCE`
> **按需同步** → `GetReplicatedProperties` + 改值后 `DOREPONCE`
> **一次性下发** → `GetInitialOnlyListReplicatedProps` + `BeginPlay` 里设值
> **禁用属性** → `GetBlackListReplicatedProps` 列出属性名

## 三、如何选择：决策指南

<img src="https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/Ycckzreplication_decision_flowchart_v1.png" width = "500">

<br>

不确定就先用 **`RepOnce`** —— 开销最小，触发时机最可控。

<br>

### 场景对照表

| 场景 | 推荐类型 | 原因 |
|---|---|---|
| 游戏阶段切换 | `RepOnce` | 阶段性变化，频率低 |
| 玩家血量 | `Lifetime` | 每帧变化 |
| 玩家积分、击杀数 | `RepOnce` | 离散事件触发 |
| 关卡一次性配置 | `InitialOnlyList` | 只关心首次值 |
| 内置但用不到的属性 | `Blacklist` | 减少无谓复制 |
| 任务进度数组 | `RepOnce` + `Lazy` | 多数时间不变，按需触发 |

## 四、实战案例

### 案例 1：游戏阶段切换（`RepOnce`）

```lua
function UGCGameMode:GetReplicatedProperties()
    return {"CurrentPhase", "Lazy"}
end

function UGCGameMode:ChangePhase(NewPhase)
    self.CurrentPhase = NewPhase
    DOREPONCE(self, "CurrentPhase")
end
```

<br>

### 案例 2：玩家血量（`Lifetime`）

```lua
function UGCPlayerPawn:GetReplicatedProperties()
    return "Health"
end

function UGCPlayerPawn:TakeDamage(Damage)
    self.Health = self.Health - Damage     -- 无需 DOREPONCE
end
```

<br>

### 案例 3：关卡配置下发（`InitialOnlyList`）

```lua
function LevelActor:GetInitialOnlyListReplicatedProps()
    return "LevelID", "Difficulty", "RecommendedPlayers"
end

function LevelActor:ReceiveBeginPlay()
    self.LevelID = self:GetCurrentLevelID()
    self.Difficulty = GameConfig.GetDifficulty()
    self.RecommendedPlayers = GameConfig.GetRecommendedPlayers()
end
```

<br>

### 案例 4：`Lazy` 列表按需同步

```lua
function EscapePlayerController:GetReplicatedProperties()
    return "EscapeCoin", "KillNums", "KillPlayerNums", {"DebugSpeLimitItemArray", "Lazy"}
end

function EscapePlayerController:GMDebugSpeDropItem()
    if self:HasAuthority() then
        local GameMode = GameplayStatics.GetGameMode(self)
        if GameMode and GameMode.EscapeItemLimit then
            self.DebugSpeLimitItemArray = ToTable_Dev(GameMode.EscapeItemLimit:GetItemListArray())
            DOREPONCE(self, "DebugSpeLimitItemArray")
        end
    end
end
```

<br>

### 案例 5：同步 C++ 预声明属性

```lua
function BTF_GameMode:InitStartSpot(StartSpot, NewPlayer)
    local PlayerState = NewPlayer.PlayerState
    PlayerState.LiveState = ExtraPlayerLiveState.InDefault
    DOREPONCE_NATIVE(PlayerState, "LiveState")    -- 属性来自 C++，用 _NATIVE
end
```

<br>

### 案例 6：禁用冗余属性（`Blacklist`）

```lua
function MyActor:GetBlackListReplicatedProps()
    return "bTearOff", "bCanBeDamaged"
end
```

## 五、常见问题

**Q1：4 种类型可以混用吗？**
可以，每个属性独立声明。如 `return "Health", {"Inventory", "Lazy"}`。

<br>

**Q2：连续多次调用 `DOREPONCE` 有问题吗？**
没有，幂等。但无意义的重复应避免。

<br>

**Q3：调用 `DOREPONCE` 后 Client 什么时候收到？**
下次网络复制时，取决于 Actor 复制频率和 DS 负载。需要立即触发可加 [`ForceNetUpdate()`](https://developer.gp.qq.com/api/#/searchContent/AActor?classDetailShow=true&path=class%2Fdetail%2FOthers%2FAActor.json&isSelect=1&apiEnc=%5B%22%E7%B1%BB%22%5D&apiLabel=AActor&autoJump=ForceNetUpdate)

<br>

**Q4：Client 能直接修改复制属性吗？**
不能，Client 修改不会回传 DS。要让 DS 感知，用 RPC（参考 [网络同步系统介绍](https://developer.gp.qq.com/wikieditor/#/catalog/203) 中"RPC"一节）。

<br>

**Q5：怎么判断属性是 Lua 声明还是 C++/蓝图预声明？**
在 `GetReplicatedProperties` 里的 → Lua 声明，用 `DOREPONCE`；不在但 Actor 上有 `UPROPERTY(Replicated)` 标记的 → 引擎预声明，用 `DOREPONCE_NATIVE`。

<br>

**Q6：`Lazy` 属性忘了调 `DOREPONCE` 会怎样？**
Client 永远收不到变化（除 Actor 首次出现的初始值）。这是"Client 没看到新值"最常见的根因。

<br>

---

## 六、最佳实践

1. **默认用 `RepOnce`（`Lazy`）**——除非高频变化或一次性配置。
2. **`DOREPONCE` 紧跟修改之后**——避免中间出错导致"改值了但忘了同步"。
3. **不要在 Client 调用 `DOREPONCE`**——同步是 DS 主动推，Client 调用无效。
4. **慎用 `InitialOnlyList`**——只对"首次出现时"的 Client 有效，后加入的 Client 收不到。UGC 玩法大部分场景用 `RepOnce` 更安全。
5. **`Blacklist` 只用于明确不用的属性**——误标会导致"Client 没收到"难排查。

<br>

---

## 注意事项

- 复制属性的 `OnRep_变量名()` 回调**无法保证顺序**，存在强依赖的属性应合并到同一 Lua Table 中一起同步（详见 [网络同步系统介绍](https://developer.gp.qq.com/wikieditor/#/catalog/203) "属性同步 - 注意事项"）。
- 同一帧内多次修改同一个属性，**只有最后一次值会被同步**，中间的修改会丢失。
- 修改后必须主动调用 `DOREPONCE` / `DOREPONCE_NATIVE` 才会触发同步，**仅赋值不会同步**。
- 复制方向固定是 **DS → Client**，Client 上的修改不会回传 DS；如需 Client → DS 通信请使用 RPC。
- "属性是否需要复制"应以业务需求判断，**默认原则是"不需要就不声明"**，避免无谓的 DS 开销。

<br>

#  使用枚举类型

绿洲启元编辑器支持枚举类型，但绿洲启元编辑器枚举类型的创建和使用与虚幻引擎稍有不同，下面会逐步介绍。
<br>
## 基本介绍

### 1. 枚举是什么？

![企业微信截图_16868353788232.png](https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/%E4%BC%81%E4%B8%9A%E5%BE%AE%E4%BF%A1%E6%88%AA%E5%9B%BE_16868353788232.png)

**枚举** （英：Enum或Enumeration）用于为整数值命名，通常用于在复数状态下（≥3）进行分类判断（对应布尔值仅支持0和1）。

例如，一个基本的游戏菜单状态可以表示为名称并编程为整数。

```js
– 0 = Mainmenu
– 1 = Game
– 2 = Pause
– 3 = Gameover
```

### 2. 绿洲枚举类型与虚幻原生枚举类型对比

所有游戏引擎都可以使用枚举，因为它们是基本的编程功能。虚幻引擎可以在c++和蓝图中使用枚举，绿洲启元编辑器继承了此特性，并支持在lua中使用枚举。<br>

| 项名 | 编辑器中创建 | 不允许与系统枚举重名 | 不允许创建同名枚举 | lua中添加自动映射 |
| ------ | ------ | ------ | ------ | ------ |
| 虚幻 | ✔ | ✖ | ✖ | ✖ |
| 绿洲（2022年4月版本） | ✔ | ✖ | ✔ | ✖ |
| 绿洲（2022年6月版本） | ✔ | ✔ | ✔ | ✔ |

<br>

## 在绿洲启元编辑器下创建枚举

### 1. 创建枚举

1.1 在【内容浏览器】的空白处右击，找到`蓝图` -`枚举` ，创建一个枚举类型产并为其命名（如“MyEnum”）。

![企业微信截图_16868353906119.png](https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/%E4%BC%81%E4%B8%9A%E5%BE%AE%E4%BF%A1%E6%88%AA%E5%9B%BE_16868353906119.png)

1.2  枚举命名注意

- 避免与系统保留枚举重名：[此API页面](https://developer.gp.qq.com/api/#/?classDetailShow=false&isSelect=1)记录了所有和平**全局保留的枚举类型**，请开发者在创建自定义枚举类型时避免与此页面下的枚举重名（2022年6月版本绿洲启元编辑器固定不允许玩家创建与系统同名的枚举）。
- 避免同一个工程下重名：同一个玩法工程下也不允许创建**同名枚举**，即便同名的枚举分别在不同的目录下。

    ![企业微信截图_16868354142099.png](https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/%E4%BC%81%E4%B8%9A%E5%BE%AE%E4%BF%A1%E6%88%AA%E5%9B%BE_16868354142099.png)

1.3 编辑枚举值

双击创建好的枚举类型资产，打开枚举值编辑界面，点击【新建】按钮为创建的枚举添加不同的枚举值，并为其命名和添加描述，点击保存来应用更改

 ![企业微信截图_16868354316452.png](https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/%E4%BC%81%E4%B8%9A%E5%BE%AE%E4%BF%A1%E6%88%AA%E5%9B%BE_16868354316452.png)

1.4 自动映射

枚举创建完毕后，绿洲启元编辑器会自动为枚举类型添加映射，写入至项目目录下`\Script\Common\ue_enum_custom.lua`文件，你可以手动将此映射require至你需要使用枚举的lua脚本以使用枚举值（2022年6月版本此映射将在玩法运行时自动加载，无需手动require）

### 2. 使用枚举

可参照如下示例使用枚举类型

2.1 蓝图设置

先创建一个要调用枚举值的Actor（如“MyActor”）。若要以蓝图变量方式存储枚举值，可在创建的Actor下新建一个变量，类型为用户自行创建的枚举类型（如“MyEnum”），你可以随时更改此变量的枚举值。

`注意：以蓝图变量方式存储枚举值非必须选项，开发者可根据具体需求选择是否需要以蓝图变量方式存储枚`

![企业微信截图_16868354621148.png](https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/%E4%BC%81%E4%B8%9A%E5%BE%AE%E4%BF%A1%E6%88%AA%E5%9B%BE_16868354621148.png)

2.2 lua脚本设置

你也可以在lua脚本中定义变量以存储和改变枚举值。

```lua
--Edit Below--
local MyActor = {
    MyEnumration = MyEnum.Banana
};
```

枚举值在计算和使用时**被视为整数**，例如定义如下枚举：

```lua
---@enum MyEnum
MyEnum = {
    Apple = 0,
    Orange = 1,
    Banana = 2,
};
```

可通过如下代码打印：

```lua
function MyActor:ReceiveBeginPlay()
    print("MyActor:ReceiveBeginPlay");
    print(MyEnum.Apple); -- 输出的值为0
end
```

这里贴出完整的示例工程代码，方便开发者参考使用，另附示例工程压缩包，请前往文章末尾的附件进行下载。

```lua
---@class MyActor_C:Actor
---@field Box UBoxComponent
---@field DefaultSceneRoot USceneComponent
---@field MyEnumeration TEnumAsByte<MyEnum>

require('Script.Common.ue_enum_custom') -- 2022年6月版本无需手动require

--Edit Below--
local MyActor = {};

function MyActor:ReceiveBeginPlay()
    print("MyActor:ReceiveBeginPlay");
    print(MyEnum.Apple); -- 输出的值为0
    print(self.MyEnumeration); -- 输出的值与MyActor蓝图中的枚举值一致
    if self:HasAuthority() == true then
        --仅在服务器运行
        self.Box.OnComponentBeginOverlap:Add(self.BeginOverlap, self);
        self.Box.OnComponentEndOverlap:Add(self.EndOverlap, self);
    end

end

function MyActor:BeginOverlap()
    print("MyActor:BeginOverlap");
    self.MyEnumeration = MyEnum.Banana; -- 输出的值为2
    print(self.MyEnumeration);
end

function MyActor:EndOverlap()
    print("MyActor:EndOverlap");
    self.MyEnumeration = MyEnum.Orange; -- 输出的值为1
    print(self.MyEnumeration);
end
```

# 新手引导

本章节介绍新手引导系统提供的 UI 模板及其使用方法。提供三种引导UI模板：新手引导组件、强引导组件、抬头HUD引导。


## 常见使用场景与基本信息

使用新手引导组件前，需要满足以下条件：

1. UGCPlayerController 上需要挂载 ``BP_UGCNewbieGuideComponent``。
2. 组件初始化完成后，才能调用 ``NewbieGuideAPI`` 注册或触发引导。
3. Client 端通常可以不传 ``playerKey``，API 会自动使用本地玩家。
4. DS 端需要传入 ``playerKey``，用来指定要操作哪个玩家的引导。
5. 引导 UI 的显示和隐藏，需要在 ``onActivate``、``onComplete`` 回调中处理。

|场景|说明|
|-|-|
|首次进入玩法|弹出欢迎说明或基础操作提示|
|点击某个按钮|引导玩家点击指定 UI|
|达到某个条件|例如玩家完成一次操作后自动触发下一步|
|多步引导|按顺序完成“打开界面 → 点击按钮 → 关闭界面”等流程|
|可重复提示|例如每次进入危险区域都提示玩家|

|项目|内容|文件说明|
|-|-|-|
|组件名称|UGC 新手引导组件|
|主要组件文件|``BP_UGCNewbieGuideComponent.lua``|挂在 UGCPlayerController 上的组件，负责初始化、进度同步和示例 UI 控制|
|对外 API 文件|``NewbieGuideAPI.lua``|对外调用入口，开发者主要通过它注册、触发和完成引导|
|配置文件|``GuideConfig.lua``|	保存触发模式、运行端、状态等常量|
|默认注册入口|``GuideRegistration.lua``|默认引导注册文件，开发者可以在这里写自己的引导配置|
|单个引导数据|``GuideEntry.lua``|单个引导的数据对象，保存引导配置和当前状态|
|管理器|``GuideManager.lua``|管理引导注册、触发、排队、完成和进度|
|支持运行端|Client / DS||
|是否支持进度保存|支持|
|是否支持多个玩家|支持，每个玩家独立管理|

## 配置细节

### 引入方式

```lua
local NewbieGuideAPI = require("ugc.UGCGame.GamePart.NewbieGuide.NewbieGuideAPI")
local GuideConfig = require("ugc.UGCGame.GamePart.NewbieGuide.GuideConfig")
```

NewbieGuideAPI 已经导出了常用枚举：

```lua
NewbieGuideAPI.TriggerMode
NewbieGuideAPI.State
NewbieGuideAPI.RunMode
```

> 注册一个引导时，需要传入一个配置表。

### 配置字段

|字段|类型|是否必填|默认值|说明|
|-|-|-|-|-|
|id|string|是|—|引导唯一 ID|
|priority|number|否|0|优先级，数值越小越先处理|
|triggerMode|number|否|Both|触发方式|
|runMode|number|否|Client|运行端|
|maxCompletionCount|number|否|1|最大完成次数，0 表示不限次数|
|prerequisites|table|否|{}|前置引导 ID 列表|
|conditionChecker|function|否|nil|轮询触发时的条件检查函数|
|condition|function|否|nil|``conditionChecker`` 的简写写法|
|onSetup|function|否|nil|注册引导时调用，常用于绑定事件|
|onTeardown|function|否|nil|注册引导时调用，常用于绑定事件|
|onActivate|function|否|nil|引导被触发时调用|
|onComplete|function|否|nil|引导完成时调用|
|userData|table|否|nil|自定义数据，可在回调中读取|

回调说明：
| 回调 | 调用时机 | 常见用途 |
|-|-|-|
| ``onSetup(entry, triggerFunc)`` | 引导注册时 | 绑定按钮点击、等级变化等事件 |
| ``onTeardown(entry)`` | 引导注销时 | 移除监听，清理临时数据 |
| ``conditionChecker(entry)`` | 轮询检查时 | 判断是否满足自动触发条件 |
| ``onActivate(entry)`` | 引导开始时 | 显示引导 UI、高亮按钮 |
| ``onComplete(entry)`` | 引导完成时 | 隐藏引导 UI、恢复界面 |

## 常用API

### 注册与触发

注册一个引导：
```
NewbieGuideAPI.RegisterGuide(config, playerKey)
```

| 返回值 | 说明 |
| --- | --- |
| `boolean` | `true` 表示注册成功，`false` 表示注册失败 |

注销一个引导：
```
NewbieGuideAPI.UnregisterGuide(guideId, playerKey)
```

手动触发一个引导：
```
NewbieGuideAPI.TriggerGuide(guideId, forceQueue, playerKey)
```

跳过当前引导：
```
NewbieGuideAPI.SkipCurrentGuide(playerKey)
```
跳过不会增加完成次数，也不会调用`onComplete`

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `config` | `table` | 是 | 引导配置 |
| `guideId` | `string` | 是 | 引导 ID |
| `playerkey` | `any` | 否 | 玩家标识，Client 端可不传 |
| `forceQueue` | `boolean` | 否 | 当前已有引导时，是否放入队列 |

## 示例


### 注册并手动触发一个引导

适合最简单的新手提示

```lua
local NewbieGuideAPI = require("ugc.UGCGame.GamePart.NewbieGuide.NewbieGuideAPI")
local GuideConfig = require("ugc.UGCGame.GamePart.NewbieGuide.GuideConfig")

NewbieGuideAPI.RegisterGuide({
    id = "guide_basic",
    triggerMode = GuideConfig.TriggerMode.Event,

    ["onActivate"] = function(entry)
        print("guide_basic 激活，显示引导 UI")
    end,

    ["onComplete"] = function(entry)
        print("guide_basic 完成，隐藏引导 UI")
    end,
})

NewbieGuideAPI.TriggerGuide("guide_basic")

-- 玩家完成操作后调用
NewbieGuideAPI.CompleteCurrentGuide()
```


### 轮询触发引导

适合“玩家满足某个条件后自动弹出”的情况

```lua
local NewbieGuideAPI = require("ugc.UGCGame.GamePart.NewbieGuide.NewbieGuideAPI")
local GuideConfig = require("ugc.UGCGame.GamePart.NewbieGuide.GuideConfig")

local bHasClickedButtonEnough = false

NewbieGuideAPI.RegisterGuide({
    id = "guide_polling",
    triggerMode = GuideConfig.TriggerMode.Polling,

    ["conditionChecker"] = function(entry)
        return bHasClickedButtonEnough
    end,

    ["onActivate"] = function(entry)
        print("条件满足，显示引导")
    end,

    ["onComplete"] = function(entry)
        print("轮询引导完成")
    end,
})

-- 某业务逻辑中改变条件
bHasClickedButtonEnough = true
```

### 事件触发引导

适合“玩家升级、点击按钮、完成任务”等事件发生后触发
```lua
local NewbieGuideAPI = require("ugc.UGCGame.GamePart.NewbieGuide.NewbieGuideAPI")
local GuideConfig = require("ugc.UGCGame.GamePart.NewbieGuide.GuideConfig")

local MockEventSystem = {
    Listeners = {},
}

function MockEventSystem:AddListener(EventName, Callback)
    self.Listeners[EventName] = Callback
end

function MockEventSystem:RemoveListener(EventName)
    self.Listeners[EventName] = nil
end

function MockEventSystem:Fire(EventName, ...)
    if self.Listeners[EventName] then
        self.Listeners[EventName](...)
    end
end

NewbieGuideAPI.RegisterGuide({
    id = "guide_level_up",
    triggerMode = GuideConfig.TriggerMode.Event,

    ["onSetup"] = function(entry, triggerFunc)
        entry.LevelUpListener = function(PlayerKey, NewLevel)
            if NewLevel >= 5 then
                triggerFunc()
            end
        end

        MockEventSystem:AddListener("LevelUp", entry.LevelUpListener)
    end,

    ["onTeardown"] = function(entry)
        MockEventSystem:RemoveListener("LevelUp")
        entry.LevelUpListener = nil
    end,

    ["onActivate"] = function(entry)
        print("玩家达到 5 级，显示升级引导")
    end,
})

-- 模拟玩家升级
MockEventSystem:Fire("LevelUp", "player_1", 5)
```

### 前置依赖引导

适合多步流程，例如“先打开背包，再选择物品”
```lua
local NewbieGuideAPI = require("ugc.UGCGame.GamePart.NewbieGuide.NewbieGuideAPI")
local GuideConfig = require("ugc.UGCGame.GamePart.NewbieGuide.GuideConfig")

NewbieGuideAPI.RegisterGuide({
    id = "guide_open_bag",
    priority = 1,
    triggerMode = GuideConfig.TriggerMode.Event,

    ["onActivate"] = function(entry)
        print("步骤 1：引导玩家打开背包")
    end,

    ["onComplete"] = function(entry)
        print("步骤 1 完成")
    end,
})

NewbieGuideAPI.RegisterGuide({
    id = "guide_select_item",
    priority = 2,
    triggerMode = GuideConfig.TriggerMode.Event,
    prerequisites = { "guide_open_bag" },

    ["onActivate"] = function(entry)
        print("步骤 2：引导玩家选择物品")
    end,
})

-- 先完成第一步
NewbieGuideAPI.TriggerGuide("guide_open_bag")
NewbieGuideAPI.CompleteCurrentGuide()

-- 再触发第二步
NewbieGuideAPI.TriggerGuide("guide_select_item")
```

### 可重复触发的引导

适合每次进入某个区域都要提示的场景
```lua
local NewbieGuideAPI = require("ugc.UGCGame.GamePart.NewbieGuide.NewbieGuideAPI")
local GuideConfig = require("ugc.UGCGame.GamePart.NewbieGuide.GuideConfig")

NewbieGuideAPI.RegisterGuide({
    id = "guide_danger_area",
    triggerMode = GuideConfig.TriggerMode.Event,

    -- 0 表示不限完成次数
    maxCompletionCount = 0,

    ["onActivate"] = function(entry)
        print("你已进入危险区域，请注意安全")
    end,

    ["onComplete"] = function(entry)
        print("危险区域提示完成")
    end,
})

-- 每次进入危险区域时触发
NewbieGuideAPI.TriggerGuide("guide_danger_area")
```

### 排队显示多个引导

同一时间只能显示一个引导。如果当前已有引导，后触发的引导会进入队列
```lua
local NewbieGuideAPI = require("ugc.UGCGame.GamePart.NewbieGuide.NewbieGuideAPI")
local GuideConfig = require("ugc.UGCGame.GamePart.NewbieGuide.GuideConfig")

NewbieGuideAPI.RegisterGuide({
    id = "guide_first",
    priority = 1,
    triggerMode = GuideConfig.TriggerMode.Event,

    ["onActivate"] = function(entry)
        print("第一个引导显示")
    end,
})

NewbieGuideAPI.RegisterGuide({
    id = "guide_second",
    priority = 2,
    triggerMode = GuideConfig.TriggerMode.Event,

    ["onActivate"] = function(entry)
        print("第二个引导显示")
    end,
})

NewbieGuideAPI.TriggerGuide("guide_first")

-- 当前 guide_first 正在显示，guide_second 会进入队列
NewbieGuideAPI.TriggerGuide("guide_second")

-- 完成第一个后，第二个会自动显示
NewbieGuideAPI.CompleteCurrentGuide()
```

### 监听引导完成

适合在引导完成后做额外处理

```lua
local NewbieGuideAPI = require("ugc.UGCGame.GamePart.NewbieGuide.NewbieGuideAPI")

local function OnGuideCompleted(GuideId, CompletionCount)
    print("引导完成:", GuideId, "完成次数:", CompletionCount)
end

NewbieGuideAPI.AddOnGuideCompletedListener(OnGuideCompleted)

-- 不再需要监听时移除
NewbieGuideAPI.RemoveOnGuideCompletedListener(OnGuideCompleted)
```

### 在默认注册文件中添加引导

开发者可以在 `GuideRegistration.RegisterGuides` 中添加自己的引导
```lua
function GuideRegistration.RegisterGuides(playerKey, isServer)
    if not isServer then
        NewbieGuideAPI.RegisterGuide({
            id = "guide_welcome",
            triggerMode = GuideConfig.TriggerMode.Event,
            runMode = GuideConfig.RunMode.Client,
            maxCompletionCount = 1,

            ["onActivate"] = function(entry)
                local NewbieGuideComponent = NewbieGuideAPI.GetLocalComponent()

                if NewbieGuideComponent then
                    NewbieGuideComponent:ShowForceClickGuideOne()
                end
            end,

            ["onComplete"] = function(entry)
                local NewbieGuideComponent = NewbieGuideAPI.GetLocalComponent()

                if NewbieGuideComponent then
                    NewbieGuideComponent:HideForceClickGuideOne()
                end
            end,
        }, playerKey)
    end
end
```

> `id` 必须唯一，建议使用清晰的命名，例如 `guide_open_bag`
> `priority` 数值越小，越优先显示
> 同一时间只会有一个引导处于激活状态
> 需要玩家操作后才完成的引导，不要在 `onActivate` 里立刻调用 `CompleteCurrentGuide()`
> 使用 `onSetup` 绑定事件时，建议在 `onTeardown` 里解绑
> Client 端引导完成后，会同步到 DS 保存进度
> 如果引导只需要在客户端显示 UI，`runMode` 建议使用 `GuideConfig.RunMode.Client`

### 粒子系统介绍

在游戏场景中存在的粒子/特效，实际上是一个粒子系统（Particle System），一个粒子系统中包括多个粒子发射器（Particle Emmitter），每一个粒子发射器包含多个模块。

### 细节编辑区

## 粒子模块介绍

特效编辑器中，每个发射器包含多个不同类型的粒子模块，可通过启用并修改粒子模块来改变发射器的表现效果。

### 基础设置

基础设置模块用于控制粒子发射的基本行为。

![image.png](https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/tHQU2image.png)

|属性名称|说明|
|:-:|-|
|发射率|设置发射器在播放期间每秒产生的粒子数量|
|爆发数量|设置单次爆发事件中瞬时生成的粒子数量|
|爆发次数|设置发射器单次播放周期内触发的爆发事件总数，设置为0时发射器会循环播放|
|持续时间|设置发射器单次播放的总时长，单位：秒|

---

### 材质

材质模块用于定义粒子渲染所使用的材质资源及其动画属性。

![image.png](https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/DKwZzimage.png)

![UV数量对比.gif](https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/HaQuHUV%E6%95%B0%E9%87%8F%E5%AF%B9%E6%AF%94.gif)

|属性名称|说明|
|:-:|-|
|发射器材质|指定用于渲染粒子外观的材质资源|
|发射顺序|控制粒子在生命周期内，如何从UV划分出的子图格序列中选择帧进行播放<br>• 无：不进行动画播放，每个粒子始终显示材质的原始完整图片<br>• 顺序：粒子按划分后的子图格，严格遵循从左到右、从上到下的顺序逐帧播放，形成连续动画<br>• 随机：粒子在播放时，从所有子图格中随机选择一帧显示，适用于产生变化丰富的非连续效果|
|UV数量|此参数将材质纹理在水平(U)和垂直(V)方向上划分为一个网格，子图格编号按从左到右、从上到下的顺序排列|
|起始|设置UV动画播放序列的起始帧编号，【发射顺序】选择“顺序”时生效|
|结束|设置UV动画播放序列的结束帧编号，【发射顺序】选择“顺序”时生效|
|对齐方式|材质的对齐方式会影响粒子大小的控制<br>• 正方形：粒子尺寸由大小相关模块的X值控制<br>![image.36.png](https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/0rKskimage.36.png)<br>• 长方形：粒子尺寸由大小相关模块的X值和Y值控制<br>![image.35.png](https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/SUSP1image.35.png)<br>• 速度：粒子尺寸受 速度在X/Y轴的分量影响（速度越快，粒子在对应方向的尺寸越大）|

### 生命内颜色

该模块用于控制粒子在整个生命周期（0~1 表示从发射开始到结束的完整周期）内的颜色与透明度变化。

![image.png](https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/9hWd6image.png)

点击颜色条的上方（颜色标签区）或下方（透明度标签区），会在对应生命周期比例位置（0~1）生成可编辑的颜色标签与透明度标签。

![dianjibiaoqian-ezgif.com-video-to-gif-converter.gif](https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/IlJ3fdianjibiaoqian-ezgif.com-video-to-gif-converter.gif)

双击标签可调整粒子对应时间点的的颜色或透明度。

![gaibianyanshetm-ezgif.com-video-to-gif-converter.gif](https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/qrjZagaibianyanshetm-ezgif.com-video-to-gif-converter.gif)

### 生命内颜色比例

生命内颜色比例模块用于控制粒子在发射过程中的颜色与透明度的叠加。粒子在生命周期中，其颜色与透明度将根据本模块的设置进行叠加计算，叠加方式为乘法混合，例如黄色叠加蓝色将得到绿色效果。该模块的操作逻辑与“生命内颜色”模块一致。

![image.png](https://cgugc-video-test-1258633575.cos.ap-shanghai.myqcloud.com/wiki_picture/GSu5rimage.png)

# 绿洲启元玩法开发框架介绍

在开发过程中，框架设计的重要性不言而喻，如果事先能对玩法开发的功能模块进行合理的规划和区分，善于利用引擎自带的框架设计，把他们放在引擎框架合理的位置中，可以省去大量设计框架和功能的时间，做到事半功倍，代码结构也可以更加清晰利于维护。

下面会介绍引擎中自带的框架设计都由哪些部分组成，以及他们的作用范围。

<br>

## DS&Client 服务器与客户端

当一局玩法开始后，会生成一个DS（Dedicated Server），DS是所有数据的权威端，一般来说，几乎所有的Actor都是在DS进行创建，然后同步到Client，在Client生成一份复制品，设置为同步的参数，在DS修改后，也会跟着同步到Client对复制品Actor的参数进行同步修改。

所以玩法逻辑也分为DS逻辑和Client逻辑，从防作弊角度来说，只有DS的数据是可以信任的，Client的所有数据都有可能被内存修改篡改，所以大部分的数据都是依靠DS的数据作为执行依据， 玩法的流程逻辑，阶段数据，击杀逻辑，比分数据，胜利判断等都是在DS执行和管理，部分纯粹表现型的功能，比如UI，则是由DS数据同步至Client，Client执行相关UI逻辑。

<br>

## Actor场景中实体的基本类型

如果需要让某个实体对象在场景中生成，那么就必须继承自Actor类型（这里指的是继承链的最底层必须为Actor）。

Actor包含Location，Rotation，Scale等在场景中确定位置的属性。同时也有网络同步的相关职能，开发者可以通过绑定Lua脚本后，重载脚本中的BeginPlay（创建时触发），EndPlay（移除时触发），Tick（每帧触发）等基本事件来完成自己所需要的功能。

后续介绍的GameMode，GameState，PlayerController，PlayerPawn，PlayerState都是继承自Actor，所以具有以上说的Actor全部功能。

### **GameMode和GameState**

- GameMode 玩法模式模块

GameMode主要用于管理玩法流程，<span style="color:red">**实例仅在DS生成**</span>（在Client无法获取到GameMode），单局玩法中只存在一个实例。是可自定义的类型中，在DS最早生成的实例。

一般用于处理一些仅在DS存在和运行的数据和逻辑，玩法流程的编写可以自行在模式编辑器和GameMode中选择一样。

- GameState 数据模块

GameState主要用于管理玩法全局数据，和GameMode一样，在DS仅存在一份实例，但是每个Client都会存在一份DS的GameState的复制品实例，所以GameState是DS全局数据同步至Client的主要桥梁。

通过属性同步可以把DS的全局玩法数据同步至各个Client，如游戏阶段的倒计时，全局分数面板等常驻参数，即时信息则使用广播RPC广播至各个Client，如全局击杀播报，胜利播报等。

### **PlayerController、PlayerPawn和PlayerState**

- PlayerController 玩家控制器模块

PlayerController主要用于管理单个玩家自身控制相关功能。DS中每一位玩家都拥有一个各自的PlayerController实例，Client中则只有该玩家自身的PlayerController复制品实例，玩家的PlayerController在自己的Client无法获取。

PlayerController适合存放与玩家自身相关而其他玩家不需要知道的参数，如击杀数，分数，金币数等，同时玩家自身相关的功能逻辑也可以在此实现，如购买道具，仅自身可以收到的通知播报等。

同时PlayerController也是玩家Client和Server交互的主要途径，所有由Client需要告知Server的消息，都是由PlayerController进行传递，比如想实现一个购买商品的功能，那么应该是由玩家点击购买按钮，由UI通知PlayerController发送一个ServerRPC，向DS申请购买物品，DS里收到申请后再进行扣款，发放物品等操作。

- PlayerPawn（PlayerCharacter）玩家角色模块

PlayerPawn主要用于管理单个玩家所控制角色相关的功能，一般为玩家所操控的人形单位实体。DS中所有存在的角色实体都对应着一份PlayerPawn实例，Client中由于存在网络同步裁剪，只能获取到自身角色一定范围内的PlayerPawn复制品实例（距离自身太远的角色可能会被裁剪导致无法获取）。

PlayerPawn合适存放玩家角色相关参数，如护甲值，攻击力，血量等，角色强相关的逻辑也推荐在这里实现（如使用道具，使用技能，播放动画等）。

- PlayerState 玩家数据模块

PlayerState主要用于管理需要在队伍中同步的相关参数。在DS中，一个PlayerController实例对应一份PlayerState实例，在Client中则有你同队（TeamID相同）的所有玩家的PlayerState实例（Client无法获取到非队友玩家的PlayerState），用途相对来说局限性比较大。

PlayerState一般仅用于存放所有队友都需要知道，但是敌人不需要知道的参数，如队伍面板需要显示的生命值，需要在小地图显示的坐标位置等）。

<br>

## UI系统

UI是玩家和游戏交互最主要的途径，需要注意的一点是<span style="color:red">**UI仅在Client存在**</span>。

在绿洲启元编辑器的用户控件编辑界面中，开发者可以创建UI的基本布局，在绑定脚本进行UI逻辑的控制，通过Construct，Tick等基础事件开发需要的功能。一般UI仅对DS同步至客户端的展示型数据进行处理和展示，开始购买商品和使用技能等逻辑则是调用Controller的ServerRPC进行申请，UI自身不储存重要的数据和执行重要的逻辑。

<br>

## 网络同步系统

网络同步系统在需要联机的玩法开发中至关重要，只有了解并掌握了网络同步系统的相关功能，才能顺利的进行玩法的开发。网络同步系统具体的介绍和使用方式在 [网络同步系统介绍](https://developer.gp.qq.com/wikieditor/#/catalog/203) 中。

<br>

## 部分内容补充

### UID

UID即玩家唯一ID，是玩家在和平中唯一标识ID，类似账号，在整个和平中，每个账号的UID都是独一无二的，主要用于一些玩家数据管理用标识，如存档接口就需要传入玩家UID来进行存档和读档。

获取方法：PlayerState.UID，PlayerController.PlayerUID

### PlayerKey

PlayerKey即玩家Key，是玩家在单局玩法中临时生成的一个标识码，在单局玩法中，该局每个玩家的PlayerKey都是唯一的，是玩法内寻找对应玩家的重要参数，大部分单局玩法获取角色实例，获取角色数据相关功能，都需要用到PlayerKey。

获取方法：PlayerState.PlayerKey，PlayerController.PlayerKey，PlayerCharacter.PlayerKey

### TeamID

TeamID即玩家队伍ID，意味着你该局中你属于哪个队伍，该参数初始值会根据玩法上传时的匹配参数决定，后续也可以通过相关接口在游戏中二次分队，获取小队成员，判断敌我阵营，以及部分和平功能，如小地图队友标记，左上角的队友状态栏等功能，都和TeamID有关。

获取方法：PlayerState.TeamID，PlayerController.TeamID，PlayerCharacter.TeamID

# 属性同步：

## 介绍：

可以对Actor中的参数进行同步，同步规则为从服务器单向同步至客户端，客户端的参数无法同步至服务器，同步方式为每隔1-X帧自动进行检测参数是否有改变（可以在Actor的NetPrioity参数中设置检测频率），把改变的参数同步至客户端。
同步开销较小，合适由DS确定，并需要持续修改且并不依赖时效性的参数，如人物属性，比赛比分等参数。需要注意的是由于是一段时间进行一次检测，如果在一帧多次修改同步参数，中间的修改会丢失，取最后一次修改的值进行同步。

## 使用方式：

1.开启同步，Actor属性面板中搜索到Replicates参数，勾选，或者在Lua脚本中调用AActor.SetReplicates函数设置<br>
2.注册同步变量，Lua脚本中新增类函数 Actor:GetReplicatedProperties()，并返回需要同步如躲猫猫案例：

```lua
local PeekabooPlayerController =
{
    IsTransform = false;
    TransformTypes = {};
}
function PeekabooPlayerController:GetReplicatedProperties()
    return
    "IsTransform",
    "TransformTypes"
end
```

3.监听同步事件，同步事件接口名为OnRep_变量名()，参考躲猫猫案例：

```lua
function PeekabooPlayerController:OnRep_IsTransform()
    print(string.format("PeekabooPlayerController:OnRep_IsTransform[%s] IsTransform[%s]", self.PlayerName, tostring(self.IsTransform)));

    UGCEventSystem:SendEvent(PeekabooModeEventType.IsTransformChange, self, self.IsTransform);
end

function PeekabooPlayerController:OnRep_TransformTypes()
    print(string.format("PeekabooPlayerController:OnRep_TransformTypes[%s]", self.PlayerName));
    log_tree("TransformTypes:",self.TransformTypes);

    UGCEventSystem:SendEvent(PeekabooModeEventType.TransformTypesChange, self, self.TransformTypes);
end
```

## 注意事项：

属性同步的OnRep响应事件有先后顺序而且无法保证顺序，所以同步参数不能存在相互的强依赖，如有强依赖的参数，可以放在一个LuaTable中进行同步。

# RPC

## 介绍：

RPC是一种服务器向客户端，或者客户端向服务器发送事件的同步方法，可以向另一端发送事件并携带所需参数。

## CallUnrealRPC

从服务器端或者客户端发起，在另一端响应的RPC，也就是DS调用会发送到客户端，在客户端调用会发送至服务器，分为可靠和不可靠类型。<br>
可靠RPC有校验机制能保证不会因为网络原因丢包导致另一端没有收到，代价则是开销更大，合适低频率发送但是要求必须收到的事件，如各种Tips。<br>
不可靠RPC则无法保证，但是同时也不容易造成网络阻塞。合适高频发送但是允许丢失的事件，如客户端向服务器发送一些高频流水数据，或者各种临时表现型的RPC（播放动画，粒子），请根据需要选择合适的方案。

### 使用方式：

可靠RPC：UnrealNetwork.CallUnrealRPC(TargetPlayerController, TargetActor, FunctionName, ...)<br>
不可靠RPC：UnrealNetwork.CallUnrealRPC_Unreliable(TargetPlayerController, TargetActor, FunctionName, ...)<br>
1.确认RPC发送端，如想向DS发送ServerRPC，在Controller或者其他Owner为Controller的Actor中增加RPC事件接口，可参考躲猫猫案例：

```
--申请点赞玩家
function PeekabooPlayerController:ServerRPC_LikePlayerByPlayerKey(Playerkey)
    print(string.format("PeekabooPlayerController:ServerRPC_LikePlayerByPlayerKey[%s], Playerkey[%d]", self.PlayerName, Playerkey));
    ......
end
```

2.注册ServerRPC，如果为客户端向DS发送的ServerRPC，需要在GetAvailableServerRPCs事件中进行注册，DS向客户端发送的ClientRPC无需注册。

```
function PeekabooPlayerController:GetAvailableServerRPCs()
    return
    "ServerRPC_ReRandomTransformTypes",
    "ServerRPC_SelectTransformType",
    "ServerRPC_LikePlayerByPlayerKey";
end
```

3.发送RPC，在客户端需要发送的地方，调用 UnrealNetwork.CallUnrealRPC/CallUnrealRPC_Unreliable。

```
--点赞按钮按下
function PeekabooPlayerlistItem:Button_Like_OnClicked()
    .......
    --发送点赞申请
    UnrealNetwork.CallUnrealRPC(PeekabooMode.OwnerController, PeekabooMode.OwnerController, "ServerRPC_LikePlayerByPlayerKey", self.PlayerResultData.PlayerKey);
     ......
end
```

## CallUnrealRPC_Multicast

从服务器端发起，广播到所有持有该Actor的客户端中的广播事件，和CallUnrealRPC类似，同样分为可靠和不可靠类型，适用于需要每一个客户端或者相关客户端都收到事件的情况下使用，比如击杀播报。

### 使用方式：

CallUnrealRPC_Multicast(TargetActor, FunctionName, ...)
CallUnrealRPC_Multicast_Unreliable(TargetActor, FunctionName, ...)
可以参考躲猫猫案例中的游戏结算事件：

```
function Action_GameSettlement:SendGameResultData()
    local GameResultData = {};
    ......
    UnrealNetwork.CallUnrealRPC_Multicast(g_current_gamestate ,"MulticastRPC_SendEvent", PeekabooModeEventType.GameEnd, GameResultData);
end

--向所有客户端广播事件
function PeekabooGameState:MulticastRPC_SendEvent(EventKey, ...)
    UGCEventSystem:SendEvent(EventKey, ...);
end
```

## 注意事项：

在同一个Actor中发送的CallUnrealRPC事件，在另一端接收可以保证接收顺序，但是在不同Actor中发送的RPC事件则无法保证接收顺序，如需严格保序的数据，建议在同一个Actor中进行发送。

# 自定义行为统计

开发者可以制定具体的数据指标来跟踪玩家的行为模式与偏好，玩法上线后通过分析这些数据，针对性优化游戏的设计与体验，包含但不限于：
- 玩家行为：某类道具的使用次数与频率如何？
- 关卡体验：关卡难度设计是否合理？玩家游玩进度情况？
- 交互设计：有多少玩家点击或触发过某按钮或功能？

绿洲启元编辑器通过自定义行为上报的API支持了特定数据的收集，并于绿洲启元管理平台提供了 [查询统计数据](https://gpeditor.qq.com/user#operationalData/2) 的途径。

<br>

## 自定义行为上报

### **SendGameTlog**

`SendGameTlog` 是目前**唯一支持正式服的日志上报接口**，适用于所有UGC玩法，不区分测试环境、灰度环境或正式服环境。

>`SendGameTlog`不支持管理平台查询数据，需提供埋点相关信息至官方运营团队做进一步拉取
>`SendGameTlog`38版本暂不支持拉取数据，如当前版本有埋点拉取需求请优先同步使用`SendPgcGameTlog`和`SendGreyTLog`

``` lua
-- 生效范围：服务器
function UGCGameSystem.SendGameTlog(Index, UID, CustomData)
end
```

- Index：日志索引，数据类型为整型，范围 `[800800, 804800]`，不同范围对应不同校验规则
- UID：玩家UID，数据类型为整型，非整型会导致上报失败
- CustomData：自定义数据，类型为表，超过512字节会进行自动截断

**使用规则**

1. 该接口仅在服务器端生效，客户端调用无效
2. 灰度和正式服均可使用，无需区分环境
3. 每个玩法实例每分钟最多调用 100 次，超过限制的调用会被静默丢弃

**Index 范围说明**

| 范围 | 用途 | CustomData 要求 |
|------|------|----------------|
| `[800800, 801800]` | 自定义 TLog | 无结构限制，可自由定义 |
| `[801801, 802800]` | 二级及以下货币 TLog | 必须包含指定字段（见下方说明） |
| `[802801, 804800]` | 物品流转信息 TLog | 必须包含指定字段（见下方说明） |

#### 货币 TLog 必填字段（Index `[801801, 802800]`）

| 字段 | 类型 | 说明 |
|------|------|------|
| `AfterMoney` | number | 变化后货币余额 |
| `iMoney` | number | 变化量 |
| `Reason` | number | 一级原因 |
| `SubReason` | number | 二级原因 |
| `AddOrReduce` | number | 增加/减少标识（1=增加, 0=减少） |
| `iMoneyType` | number | 货币类型 |
| `CustomData` | table | 扩展数据（可为空表 `{}`） |

#### 物品流转 TLog 必填字段（Index `[802801, 804800]`）

| 字段 | 类型 | 说明 |
|------|------|------|
| `iGoodsType` | number | 物品类型 |
| `iGoodsId` | number | 物品 ID |
| `iGoodsName` | string | 物品名称 |
| `iCount` | number | 变化数量 |
| `AfterCount` | number | 变化后数量 |
| `Reason` | number | 一级原因 |
| `SubReason` | number | 二级原因 |
| `AddOrReduce` | number | 增加/减少标识（1=增加, 0=减少） |
| `CustomData` | table | 扩展数据（可为空表 `{}`） |

**注意事项**

1. CustomData 内不要嵌套过深，建议保持在 2-3 层以内
2. JSON 中的 `|`（竖线）会被替换为空格（后台规则），避免在数据中使用
3. 设计 CustomData 结构时注意精简字段名，优先使用短键名

## 案例演示

抽奖是游戏中较为常见的一类功能，玩家通过抽奖行为获得预设的相对应的奖励，开发者要验证抽奖概率的准确性就依赖有效的玩家数据作为基准进行分析。以跟踪和分析玩家在游戏中的抽奖行为为例，做一个简单的演示。

如下所示，设计了一个具有三种奖品的奖池，每当一个奖品被抽中时，就将该事件进行上报。

|抽奖奖品|中奖概率|中奖行为ID|
|-|-|-|
|AKM|40%|800800|
|M416|30%|800801|
|AUG|30%|800803|

---

**抽奖行为上报**

``` lua
function Lottery:LotteryHandle(PlayerKey)
    -- 判断PlayerKey以及PlayerKey的有效性
    if not PlayerKey or not UGCGameSystem.GetPlayerPawnByPlayerKey(PlayerKey) then return end

    -- 自定义一个奖品列表
    local rewardInfo = {
        result001 = {
            resultId = "AKM",
            eventId = 800800,
            rate = 40
        },
        result002 = {
            resultId = "M416",
            eventId = 800801,
            rate = 30
        },
        result003 = {
            resultId = "AUG",
            eventId = 800803,
            rate = 30
        },
    }

    -- 预创建抽奖结果，随机数
    local result = rewardInfo.result001
    local rate = math.random(1,100)

    local addNum = 0
    for k,v in pairs(rewardInfo) do
        if rate <= addNum + v.rate then
            -- 真实抽奖结果赋值
            result = v
            break
                                else
                                                addNum = addNum + v.rate
        end
    end

    -- 上报抽奖结果事件（使用推荐的 SendGameTlog 接口）
    local uid = UGCGameSystem.GetUIDByPlayerKey(PlayerKey)
    UGCGameSystem.SendGameTlog(result.eventId, uid, { resultId = result.resultId })

end
```

在这段代码逻辑中，我们设计了一个简单的抽奖功能，在处理抽奖结果中上报了该行为事件。

如上所示，当抽奖结果result返回后，使用 ``UGCGameSystem.SendGameTlog`` 将结果进行上报，其中 ``eventId`` 对应的是每次抽奖结果的事件，一共有三个抽奖奖品，对应的事件ID分别为：800800，800801，800803。

> **注意：**
行为上报只作为收集数据的方式，不应当对游戏流程产生任何的阻塞，并破坏玩家的游戏体验。
